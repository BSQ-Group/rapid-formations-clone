## 3. What was done
Root cause: the page's imported Lexical content represents every nested sub-list as a
content-less wrapper `<li class="nestedListItem">` sitting in the list flow (either as a root-
level sibling list wrapping one such listitem, or as a sibling listitem inside an existing list's
own children) instead of nesting the sub-list directly inside the clause `<li>` it belongs to.
This both restarts/shifts native counters (AC1/AC2) and adds real extra `<li>` rows the browser
renders (AC3), regardless of the predecessor's counter-suppression CSS.

Extended `scripts/fix-privacy-policy-clause-lists.ts` with two more transforms on top of the
existing list-run merge:
- `unwrapDoubleList` — collapses `list > listitem(sole child: list) > list` down to the real
  inner list (an import double-wrap artifact).
- `foldWrapperSiblings` — within one list's own children, folds a listitem whose children are
  entirely nested lists into the immediately preceding sibling's children.

Ran `--live` against the local Payload DB (with `context: { disableRevalidate: true }` added to
the `payload.update()` call — the bare script has no Next.js request-context for the page's
`revalidatePath` afterChange hook, which threw `Invariant: static generation store missing`
without it). Verified via direct re-query: total `<li>` 203 → 187, exact match to live.

Updated `TextContent.styles.ts`'s `policy` variant: dropped the now-dead `.nestedListItem`-scoped
rules (that class never renders after the content fix) for structural equivalents —
`[&_li_ul]:list-[lower-roman]` / `[&_li_ul>li]:!my-0` — so any `ul` nested inside a clause `<li>`
gets roman markers and live's tight item pitch, regardless of section.
