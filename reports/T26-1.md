# T26 — CORE-7345 report

## 1. Summary
`/compare-packages/llp/` feature-list order at a true 360px viewport had "Free Client Portal to
Manage Your Companies" before "Company Registers with First Entries", the reverse of Live's order
at that breakpoint. Fixed by swapping the two items in the mobile-only render path
(`MobileCarousel.tsx`), scoped to the `llp-package` slug only. Desktop (≥768px) is untouched and
was already correct.

## 2. Root cause
Both `DesktopGrid` and `MobileCarousel` (`src/blocks/ComparePackageTable/`) render from the same
single `data.products` array (`ComparePackageTableView.tsx` renders both components side by side,
toggled visible/hidden by `hidden md:block` / `block md:hidden`). That array's order comes from
the LLP package's `products` field in the CMS (Mongo `packages` collection, doc id
`6a8c21ec554f4d9a40c07b87`, slug `llp-package`) — one flat, unordered-per-breakpoint list. Verified
via a direct Mongo query (bypassing the broken local Next build, see §4) that in that array, index
4 = "Free Client Portal…" and index 5 = "Company Registers…" — i.e. Free Client Portal first. That
order is correct for ≥768px (Live matches it there per the ticket's own evidence table) but wrong
for <768px, where Live shows Company Registers first. Since one CMS array feeds both breakpoints
with no existing mechanism for a breakpoint-specific override, the code had no way to diverge — it
rendered the same order everywhere, matching Live at ≥768px and mismatching at 360px.

## 3. Fix
`src/blocks/ComparePackageTable/MobileCarousel.tsx`: added `MOBILE_PRODUCT_ORDER_SWAP`, a
slug-keyed map of `[beforeId, afterId]` product-id pairs, and `applyMobileProductOrder()`, which
swaps the two ids' positions only if `beforeId` currently comes after `afterId` (no-op otherwise —
safe against future content edits reversing the order in the CMS). Applied only inside
`MobileCarousel`'s `cards` computation, keyed on `pkg.slug === 'llp-package'`. `DesktopGrid.tsx` is
untouched. No other compare-packages page's slug matches the map key, so `/compare-packages/
guarantee/` and all others are structurally unaffected (confirmed by reading the swap function —
it's a no-op unless the exact slug key is present in the map).

## 10. Task-quality feedback
- Ticket was accurate and well-evidenced (exact before/after item order, per-breakpoint match
  table, both screenshots) — good ticket, no ambiguity about *what* was wrong.
- What was missing: the ticket doesn't state *why* Live itself has different orders at different
  breakpoints for this one package (probably a hand-authored quirk on Live, not a systematic
  pattern) — worth noting for future similar tickets that "swap on mobile only" bugs may require a
  code-level per-breakpoint override, not just a CMS content reorder, since a naive content-only
  fix (reordering the CMS array) would fix one breakpoint and break the other. A future version of
  this ticket type could flag "check whether desktop/mobile share one data source before assuming
  a content fix" to save the round-trip.
- Friction: the worktree's Turbopack/symlink build failure (see §4) is a recurring, already-known
  issue (matches `rf-t8/reports/T8-1.md` verbatim) that ate a large fraction of this task's time
  and blocked all live verification. Suggest a rule: **check sibling lanes' most recent report(s)
  for this exact error signature before spending time on multiple restart/workaround attempts** —
  I only found T8's report by chance while writing this one; had I checked first I'd have stopped
  investigating build workarounds after the first `rm -rf .next` retry instead of trying webpack
  fallback / env-var / symlink-form variations.
- Task was right-sized (S effort, single-file fix) once the actual defect was understood; the
  friction was entirely environmental, not scope-related.
