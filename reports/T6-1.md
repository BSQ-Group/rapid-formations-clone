  `BankingPartners` logos), `img.naturalWidth` is *density-corrected* per the HTML/WHATWG spec:

  1×. Spent significant time diagnosing this (independently re-fetching and decoding the exact
  `currentSrc` bytes via `createImageBitmap` to prove the served bytes were actually correct)
  before realizing it was a measurement artifact, not a regression. Anyone re-running this AC
  in future should fetch+decode the actual bytes rather than trusting `img.naturalWidth` for
  x-descriptor images.

## 10. Task-quality feedback
- **Accurate but the measurement methodology in the AC was wrong.** AC#3 prescribes
  `naturalWidth / rendered CSS width` as "effective DPR." This is unsound for any image using
  density (`x`) descriptor `srcset` selection (the common case for fixed-width `next/image`
  usage without a `sizes` prop) — the HTML spec mandates `naturalWidth` be density-corrected,
  so a *correctly* 2x-served image measures as exactly 1× by this formula, producing a false
  "still broken" signal. **Suggestion**: future ACs that prescribe a resolution-measurement
  formula should say "fetch+decode the actual served bytes (`createImageBitmap` on the
  `currentSrc` response), not `img.naturalWidth`" — otherwise a diligent re-verification will
  reproduce the exact false-negative this task nearly fell into.
- **Right-sized** otherwise — the AC's framing (confirm-first, don't re-fix, don't widen scope)
  was exactly right and the actual remaining work (verify CMS state, clean the rescued branch,
  re-measure, ship) fit in one focused round once the measurement issue was diagnosed.
- **Friction**: the HEARTBEAT.md path given in the task brief
  (`rapid-formations-clone/.claude/HEARTBEAT.md`) does not match what CONTROL's watchdog reads
  (`rapid-formations-clone-task-state/.claude/HEARTBEAT.md`). Worth fixing the brief template so
  the next resumed lane doesn't look stalled for 15+ minutes for the same reason.
- **Rule suggestion**: when a lane resumes rescued work from a SIGTERM kill, explicitly note in
  the resume brief whether any DB/CMS-side mutations the killed session ran (as opposed to
  git-tracked file changes) may have already landed — this task's AC#1 ("confirm first whether
  already re-uploaded") only existed because of exactly that risk, and it turned out to be the
  actual state. A generic "assume nothing happened, redo from scratch" resume instruction would
  have caused a wasted duplicate re-upload.
