## 1. Task
CORE-6963 · [RF] / — FAQ caret icon doesn't rotate/animate on open (Key questions accordion).
Ticket claims: on the clone, the FAQ caret has `transition-duration: 0s` / `transform: none` even
when open, vs Live's `transition: all 0.35s ease` smooth rotation.

## 2. What was done
- Fetched the live Linear ticket (MCP worked despite the session banner saying `linear` needs
  auth — see field 4) and wrote 5 concrete acceptance criteria into `tasks/T1.json` (committed to
  `task-state`, commit `1c353ce`).
- Attempted local repro: dev server on port 3008 was down; one port-scoped restart attempt hit the
  known repo-wide `TurbopackInternalError: Symlink [project]/node_modules is invalid` (both
  `bun run build` and `bun run dev`'s underlying `next build`/`next dev` fail identically). Per the
  task brief's documented workaround, did not touch `next.config.ts`; relied on `bun ts` (clean)
  and the deployed clone prod (`https://rapid-formations-clone.vercel.app/`, which serves current
  `main`) for live verification instead — my branch has zero commits ahead of `main` at this point.
- Found the FAQ caret code: `src/components/shared/Collapsible/Collapsible.tsx` +
  `Collapsible.styles.ts`, used exclusively by `src/blocks/FAQs/Component.tsx` (confirmed via grep
  — no other block imports `Collapsible`), which renders the homepage "Key questions" accordion.
  Rotation is `rotate-180` + `transition-all duration-350` on the icon-wrapper `<span>` (not the
  inner FontAwesome `<svg>` itself — an architecture difference from Live's `svg.fa-angle-down`,
  but that only matters if it breaks the visual rotation, which it doesn't: rotating the parent
  visually rotates its child).
- **Root-cause investigation turned up that this exact defect was already fixed on `main`**, three
  weeks before this task was picked up: commit `96aa259` (2026-08-25, "fix(faq): revive the dead
  duration-[350ms]...") registered `theme.transitionDuration[350] = '350ms'` in
  `tailwind.config.mjs` and switched the Collapsible's classes from the inert arbitrary
  `duration-[350ms]` (no matching Tailwind utility was ever generated for it, so the browser fell
  back to `transition-all`'s implicit 0s/default duration — the exact "0s, no rotation" symptom
  CORE-6963 reports) to the now-real named `duration-350` utility. That commit was NOT filed under
  CORE-6963 and doesn't reference it, but its diff is precisely CORE-6963's root cause.
- Verified empirically with a REAL click against the deployed clone prod, using a small diagnostic
  script (gated through the shared `pw-slot.ts` machine-global Chromium concurrency lock — not an
  unthrottled ad-hoc launch) since `pw-capture.ts` is screenshot-only and has no click/interaction
  or computed-style-read capability:
  - Located the actual "Key questions about forming a company" `<h2>`, scoped to its ancestor
    `<section>`, and measured the first FAQ trigger's icon wrapper before/mid/after a real mouse
    click, at all 4 required breakpoints (360/768/1024/1800).
  - **Before click** (all 4 breakpoints): `wrapperTransition: "0.35s cubic-bezier(0.4, 0, 0.2, 1)"`,
    `wrapperTransform: "none"`.
  - **200ms after click** (mid-transition, all 4 breakpoints): `wrapperTransform:
    "matrix(-0.76…, 0.65…, -0.65…, -0.76…, 0, 0)"` — a partial rotation matrix, proving the
    animation is actually interpolating frame-by-frame, not snapping.
  - **Settled** (all 4 breakpoints): `wrapperTransform: "matrix(-1, 0, 0, -1, 0, 0)"` (=180°),
    `aria-expanded="true"`.
  - This is the opposite of the ticket's reported symptom (`transition-duration: 0s`,
    `transform: none` even when open) — on current `main`/clone-prod the caret smoothly rotates
    180° over ~0.35s on every click, at every required breakpoint.
- Conclusion: **CORE-6963 is stale/already-resolved on `main`**. There is no code defect left to
  fix in this repo — implementing "a fix" now would mean either a no-op branch or reintroducing
  churn on already-correct code, neither of which is a real deliverable. Per the task's own hard
  boundary language ("if the real defect turns out to be [something else]... file a proposal, set
  your task back, and stop" — the closest-fitting existing guidance for an unexpected-state
  finding), and because none of the automated ship paths (PR / `ready` / `restart-from-scratch`)
  actually model "ticket already resolved upstream, nothing to change," stopped here to report to
  the user rather than force a transition that doesn't fit, or fabricate a change.

## 10. Task-quality feedback
- **The task was NOT accurate at pickup time** — the underlying defect it describes was already
  fixed on `main` 10 days before this task's `createdAt` in `tasks/T1.json`
  (`2026-09-01T13:50:58Z`) and 3 weeks before this round ran. The Linear ticket itself was last
  updated `2026-09-03T16:40:39Z` with a note acknowledging the originally-reported "slower spin"
  framing was measured as "no transition at all" — but that measurement evidence (screenshots
  dated at ticket creation, 2026-08-10) still predates the 2026-08-25 fix commit. Nobody re-verified
  against current `main` before scheduling/dispatching this task.
  **Suggestion**: before a stale-looking bug ticket (created weeks ago, `Todo` status, no recent
  ticket-side re-verification) is dispatched to a worker, a cheap pre-flight — one automated
  click-test against current clone-prod for the reported symptom — would catch "already fixed
  upstream" tickets before spending a full worker round on them.
- **Missing from the task brief**: no guidance for the "ticket's root defect no longer reproduces"
  outcome. Every other branch (fix found → PR; fidelity issue found → proposal + backlog) is
  covered; "nothing to fix, already resolved" is not. This is exactly the situation the task's own
  "if in doubt... stop" framing seems to want, but the *mechanism* to stop cleanly (which task
  status, whether to touch Linear) isn't specified.
  **Rule suggestion**: add a documented `TaskAction`/status combination (or explicit brief
  instructions) for "verified already-fixed on main, no diff to ship" distinct from both
  `restart-from-scratch` (implies a redo) and `submit-pr` (implies a real diff) — e.g. a
  `resolved-upstream` outcome that leaves the task for human triage against the Linear ticket
  without implying failure or requiring a fabricated PR.
- **Friction**: `pw-capture.ts` and `clone-qa-interaction` (the two sanctioned browser tools)
  don't cover "click and read computed style / prove a CSS transition animated," and
  `clone-qa-interaction`'s selectors are hardcoded to one other block's DOM conventions. A
  general-purpose "click a selector, diff computed style before/mid/after" utility (built on the
  existing `pw-slot.ts` concurrency gate) would remove the temptation for every lane investigating
  an animation/interaction bug to write its own one-off script.
